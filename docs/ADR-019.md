# ADR-019 — "Kavach": Open-Source Family Safety & MDM Platform

**Date:** 2026-09-12
**Status:** Proposed
**Deciders:** @carponoid

---

### Context

Google Family Link manages our household (6 members, 2 supervised kids) but does
not scale for a family scattered across the globe:

- **Play Store country lock-in** — the whole account clings to one country's
  store with no clean way to switch, breaking app availability for members in
  different regions.
- **All-or-nothing model** — coarse controls, weak per-device flexibility.
- **Cloud dependency** — location, app data, and screen-time telemetry live on
  Google's servers; no ownership or portability.

We already self-host most of the "family cloud" primitives on the JGK/shambala
stack: **Nextcloud** (files), **Immich** (photos), Cloudflare Tunnel + Zero
Trust (edge), rootless podman + systemd (runtime). The gap is the **safety /
device-management layer**: MDM, content filtering, and location/find-my-device.

**Goal:** replace *all* Google Family features from Day 1 with a ground-up,
opensource, low-overhead subsystem — codename **Kavach** (कवच, "shield") — that
plugs into the existing stack rather than reinventing files/photos.

**Constraints:**
- Host: **shambala** (aistack host), rootless podman, `2426X` port scheme.
- Devices: **Android only** — a mix of stock (with Google) and de-Googled /
  GrapheneOS-friendly handsets. **No iOS** → no Apple APNs/MDM cert burden.
- Single-SSO for the family across every service.
- "Less overhead" — prefer assembling small, purpose-built OSS over a monolith.

---

### Decision

We will build **Kavach** as a *composition of focused OSS components*, each
owning one Google-Family capability, unified by DNS-level policy and a single
identity provider. **No single tool replaces Family Link**; the robustness comes
from the composition.

| Capability (Google Family) | Kavach component | Host port | Rationale |
|---|---|---|---|
| Content / site filtering, SafeSearch, YouTube-restricted | **AdGuard Home** | `24278` (web UI) + `53` (DNS) | Per-device DNS profiles; strongest, lowest-overhead lever; forced SafeSearch. **Chosen over NextDNS** — see "DNS filter" decision below |
| **Request-access approval** (kid requests a blocked site → parent approves) | **kavach-approver** (custom) | `24282` | Custom block page + approve webhook; pings parent via Telegram/Hermes; adds per-client allowlist via AdGuard API |
| Location tracking + history + geofences | **Traccar** | `24279` | Purpose-built GPS server; geofence enter/exit alerts; OwnTracks/Traccar-Client apps |
| Find my device / ring / lock / locate / wipe | **FMD Server** (FindMyDevice) | `24280` | Self-hosted, E2E-encrypted command channel |
| App management, install control, kiosk, restrictions | **Headwind MDM** | `24281` (+ pod-internal PostgreSQL) | Open-source Android MDM; push APKs region-independently (kills Play-Store lock-in) |
| Identity / SSO across all of the above | **Nextcloud-as-IdP** (existing) or Authentik | reuse existing | One family login; kids get scoped accounts |
| Files / photos | **Nextcloud / Immich** (existing) | reuse existing | Already deployed |
| Schedule limits ("bedtime") | **AdGuard per-client scheduled blocking** + Headwind kiosk | — | Blackout windows enforced at DNS + launcher layer |

**Play-Store lock-in — the core fix:** de-Googled devices use **F-Droid +
Aurora Store**, and Headwind MDM pushes APKs directly by region, sidestepping
the single-country Play account entirely. Stock-Android members keep Play but
gain the self-hosted safety layer on top.

**DNS filter: AdGuard Home, not NextDNS.** The deciding factor is the
**request-access approval workflow** the parent wants: a kid hits a blocked
site, taps *Request access*, the parent is notified, and approves. NextDNS is
SaaS with a **fixed, non-customisable block page** — no way to add a request
button or wire an approval channel. AdGuard Home is self-hosted with a full
**REST API** and a **Custom-IP block redirect**, so we can serve our own block
page and programmatically allowlist per client. NextDNS is retained only as an
emergency fallback resolver.

**Request-access flow:**
```
Kid hits blocked site
  → AdGuard returns Custom IP = block-page host (blocked.thepkb.in)
  → Block page shows the domain + [Request access]
  → POST {kid, domain} → kavach-approver (24282)
  → Approver notifies parent via Telegram (Hermes bridge): [Approve 1h] [Approve ∞] [Deny]
  → Parent approves → approver calls AdGuard API: add domain to that client's allowlist (temp/perm)
  → Kid retries → loads ✓
```
The only net-new code is the small **kavach-approver** container (block page +
approve webhook + AdGuard API client + Telegram). Everything else is config,
reusing the existing Hermes/Telegram + Cloudflare Tunnel plumbing.

**HTTPS caveat:** the Custom-IP redirect is seamless over HTTP; HTTPS sites
show a TLS warning before the block page (we're intercepting). Mitigation:
issue an internal CA cert for `blocked.thepkb.in` and push it as a trusted cert
via MDM (device-owner enrollment) so the block page loads cleanly. Another
reason MDM + de-Googled devices pay off.

**Enforcement backbone = DNS.** AdGuard Home with **per-client** configs is the
spine: SafeSearch enforcement, adult/category blocking, and time-scheduled
blackouts. For the initial rollout, managed Android devices use **app-based
DoH over HTTPS** (`https://dns-kavach.thepkb.in/dns-query`) rather than raw DNS
ports on the host. Native Android **Private DNS** remains an **optional second
path** via DoT on `:853` for later, when we decide whether to add a host-level
privileged-port helper. MDM "device owner" provisioning locks the chosen DNS
path so kids can't toggle it off.

### Deployment Topology (resolved)

**All Layer-1 services run on shambala as rootless-podman containers inside a
single pod named `kavach`**, managed by a user-level systemd unit — same pattern
as the existing aistack pods.

```
pod: kavach  (shambala, rootless podman, `kavach-pod.service` user unit)
 ├─ kavach-dashboard   :24284 (portal)                      ← published
 ├─ kavach-adguard     :24278 (UI) + :24283 (DoH origin)    ← published
 ├─ kavach-traccar     :24279 (host loopback)               ← published
 ├─ kavach-fmd         :24280 (host loopback)               ← published
 ├─ kavach-mdm         :24281 (host loopback)               ← published
 ├─ kavach-approver    :24282 (host loopback)               ← published
 └─ kavach-mdm-db      :5432  (pod-internal only)           ← NOT published
cloudflared → kavach.thepkb.in (dashboard + /apps/* path proxies) and dns-kavach.thepkb.in (DoH)
            → pod loopback ports
optional later: direct DoT `:853` with host-level privileged-port assist
```

**Implications of the single-pod choice:**
- **Shared network namespace** — all containers reach each other on `localhost`
  (`kavach-approver` → AdGuard `localhost:24278`; Headwind → PostgreSQL
  `localhost:5432`). No inter-container DNS. Ideal for the approver ↔ AdGuard
  API path.
- **No duplicate ports inside the pod** — every service + internal helper port
  must be unique across the pod. Published by default: `24278–24284`.
  Pod-internal (never published to host): PostgreSQL `5432` and any backend ports.
- **One lifecycle** — `systemctl --user {start,stop} kavach-pod` cycles the
  whole family stack. Trade-off: no independent per-service restart without
  touching the pod; acceptable for a family stack (simpler > granular).
- **Security fit** — only the 5 service ports bind host **loopback**; nothing on
  `0.0.0.0`. `cloudflared` is the sole public ingress, satisfying the
  edge-only-gate rule from the Access section.

### Rollout Phases

**Phase 1 — MVP (the three chosen Day-1 priorities):**
1. **Location + Find/Ring** — Traccar (`24279`) + FMD Server (`24280`), one kid
   device enrolled end-to-end (locate, history, ring).
2. **Content filtering** — AdGuard Home (`24278`) with per-client SafeSearch +
  adult-category blocklists; supervised devices pointed at it via a managed
  DoH app path.
3. **App/MDM enrollment** — Headwind MDM (`24281`), enroll one device as device
   owner, push/whitelist an app, lock DNS settings.

**Phase 2 — Hardening:**
- Scheduled blackout windows (bedtime) in AdGuard per client.
- SSO wire-up (Nextcloud/Authentik) so all four consoles share one login.
- Geofence alerts (school/home) via Traccar → Telegram (reuse Hermes bridge).
- Optional native Android **Private DNS** path via DoT on `:853` if we later add
  a host-level privileged-port helper or other TCP-capable edge for raw DNS.

**Phase 3 — Screen-time (the hard gap):**
- Custom kids launcher / Headwind kiosk app-time policies; accept this is
  *assembled*, not turnkey (see Trade-offs).

**Edge:** each web console fronted by Cloudflare Tunnel + Zero Trust Access
(`*.thepkb.in`), consistent with the rest of the stack.

### Device Lockdown Scope (resolved)

Android provisioning level decides **whether a kid can undo the controls** — the
single most important device decision. Three modes:

| Mode | Control | Reset needed? | Bypass risk | Use for |
|------|---------|---------------|-------------|---------|
| **App-only** (sideload) | Just installs tracker/DNS apps | No | **High** — kid can toggle Private DNS off, uninstall apps | Trusted teens / soft rollout |
| **Profile Owner** (work profile) | MDM controls a managed profile; personal side stays kid's | No | **Medium** — personal-side DNS/browser still kid-controlled; filtering not global | BYOD teens, some managed apps |
| **Device Owner** (fully managed) | MDM controls the **whole device** | **Yes (factory reset + enroll)** | **Low** — DNS locked, uninstall/reset/USB-debug blocked | **The 2 supervised kids** |

**Only Device Owner makes filtering un-bypassable.** It can lock the chosen DNS
path, disable factory reset / safe-mode / USB-debug, force location on, block
uninstalls, whitelist apps, run a kiosk launcher, and install the **internal CA
cert** for a clean HTTPS block page. In practice the two enforceable DNS modes are:

- **Primary now:** a managed DNS/VPN app pinned to the AdGuard **DoH** endpoint
  over HTTPS.
- **Optional later:** Android native **Private DNS** pinned to the AdGuard **DoT**
  hostname on `:853`.

**Critical dependency chain:**
```
Un-bypassable global filtering
  ⇒ requires  Locked DNS path (primary: managed DoH app, optional: native DoT)
  ⇒ requires  DEVICE OWNER provisioning
  ⇒ requires  Factory reset + fresh enrollment (QR / afw)
```
Without device-owner, AdGuard filtering is **advisory** — one settings toggle
or app uninstall away from off.

**Per-member recommendation:**

| Member | Mode | Rationale |
|--------|------|-----------|
| 2 supervised kids | **Device Owner** | Only mode where DNS-lock + anti-bypass hold |
| Older/trusted teens | Profile Owner or App-only | Less friction, partial control |
| Adults (self/spouse) | App-only, opt-in | Consent-based location share, no lockdown |

**De-Googled synergy:** provision Device Owner during the same fresh
GrapheneOS / de-Googled flash — wiping anyway, so lockdown + F-Droid/Aurora +
Play-Store-country fix all land in one pass.

**Caveat:** Headwind device-owner provisioning on **GrapheneOS** can be finicky
(hardened provisioning path); smoother on stock-AOSP / de-Googled LineageOS.
Test on one device in Phase 3 before committing all kids.

### DNS Reachability (resolved)

**Phase-1 default: managed Android devices use app-based DoH, not raw DNS on
the host.** AdGuard's encrypted DNS origin is published on loopback `:24283`, and
`cloudflared` can expose it as `https://dns-kavach.thepkb.in/dns-query` over
standard HTTPS. This works globally and keeps the entire Kavach pod rootless.

**Important Android correction:** the built-in Android **Private DNS** feature is
**DoT on `:853`**, not DoH. So `https://.../dns-query` is **not** a valid value for
the native Private DNS field. If we later want the app-less Android path, we must
offer a real DoT listener on `:853`, which in turn needs a host-level privileged
port helper or another edge that can carry raw TCP 853.

**Result:**

- **Primary now:** DoH-over-HTTPS for managed devices, via a pushed DNS/VPN app.
- **Optional later:** native Android Private DNS over DoT `:853`.
- **Not part of initial rollout:** classic DNS on host `:53`.

### Consequences

**Good:**
- **Full data ownership** — location, app inventory, filtering logs stay on
  shambala.
- **Region-independent apps** — Headwind + Aurora/F-Droid kill the Play-Store
  country lock, the original pain point.
- **Reuses existing stack** — files/photos/edge/SSO already exist; only the
  safety layer is net-new.
- **Composable & replaceable** — each capability is an isolated container; swap
  one without touching the others.
- **Low marginal overhead** — four small containers, all rootless podman under
  the existing systemd/pod pattern.

**Bad / Trade-offs:**
- **Screen-time is the weak spot** — no OSS tool matches Family Link's per-app
  daily limits; approximated via DNS blackouts + kiosk launcher. Assembled, not
  turnkey.
- **Bypass resistance** — stock (non-device-owner) Android can toggle DNS/Wi-Fi.
  Full lockdown needs device-owner provisioning (factory reset + enroll), best
  done on de-Googled handsets.
- **More moving parts** than one SaaS — four services to run, patch, and back
  up (mitigated by podman + existing backup patterns).
- **Native DNS standards still want privileged ports** — Android native Private
  DNS wants DoT on `:853`, and classic DNS wants `:53`. The initial managed-device
  rollout avoids both by using DoH over standard HTTPS, but app-less Android or
  LAN-router adoption later will still need a host-level privileged-port strategy.

### Access & Single Sign-On (resolved)

**Decision: gate at the edge with Cloudflare Access federated to Google /
GitHub / Microsoft — no self-hosted IdP.** A single Kavach dashboard
(`kavach.thepkb.in`) is the only Layer-1 web entrypoint. The dashboard reverse
proxies Layer-1 apps on path routes (`/apps/adguard`, `/apps/traccar`,
`/apps/fmd`, `/apps/mdm`, `/apps/approver`) so one Access session is reused
across the whole portal.

**Why not per-app SAML:** AdGuard and FMD have **no external SSO** support — the
two we most need gated. Edge-gating sidesteps the gap: auth happens before the
request reaches the app, so the app's own login support is irrelevant.

**"Invisible second layer" — SSO feel, no repeated OAuth prompts (UX-critical).**
Cloudflare Access authenticates once on `kavach.thepkb.in`; portal path proxies
carry that session to all Layer-1 UIs under the same host.

| Surface | Method | User experience |
|--------|--------|-----------------|
| `kavach.thepkb.in` | CF Access OAuth (GitHub) | Primary login |
| `/apps/*` paths | Same-domain reverse proxy | Reuses existing Access session |
| `dns-kavach.thepkb.in` | Separate DoH endpoint | Not part of interactive dashboard SSO |

**Net:** one social login → one dashboard → every Layer-1 UI via dashboard path
links without extra OAuth handshakes.

**Hard security requirement:** every Layer-1 app binds to **loopback / the
tunnel network only** (`127.0.0.1:2427x`), never `0.0.0.0`. `cloudflared` is the
sole public ingress. `kavach-approver` → AdGuard API calls stay on the internal
network (bypass the gate, keep working). Keep a **break-glass** path (SSH tunnel
to loopback) in case CF/DNS is down.

### Alternatives Considered

| Option | Pros | Cons | Rejected because |
|--------|------|------|-----------------|
| **Stay on Google Family Link** | Zero effort, mature screen-time | Play-Store country lock, no data ownership, doesn't scale globally | Is the problem we're solving |
| **Single monolith MDM (e.g. Fleet, Miradore)** | One console | Fleet is osquery/enterprise-oriented, heavy; no content-filter or family location; still no app-region fix | Overhead + poor family fit |
| **NextDNS (SaaS) instead of AdGuard** | Zero-maintenance, great parental presets | Not self-hosted; recurring cost; telemetry off-box; **fixed block page → no request-access/approve flow** | Can't build the parent-approval workflow; kept only as emergency fallback resolver |
| **PhoneTrack (Nextcloud app) instead of Traccar** | Stays inside Nextcloud, no new service | Fewer geofence/alert features, less robust than purpose-built GPS server | Traccar is more robust for the tracking MVP; PhoneTrack noted as lightweight alt |
| **Self-hosted IdP (Authentik/Keycloak) for SSO** | One user directory, real OIDC/SAML | Another service to run; AdGuard/FMD still need proxy-auth anyway | CF Access federated to Google/GitHub/MS gives the same SSO with zero extra services |
| **Per-app SAML into Google/GitHub/MS** | "Proper" SSO per app | AdGuard & FMD have no external SSO; Headwind social SSO absent | Fails on the exact apps we most need gated |
